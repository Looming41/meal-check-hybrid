# 밥상 판정 — 하이브리드 버전

질환이나 상태를 고르고 음식 사진을 찍으면 각각의 식이 기준에 따라 판정해 주는 앱. 전 연령 대상이다. 이전 Gemini 버전과 근본적으로 다른 점은 **AI가 판정하지 않는다**는 것이다.

```
사진 ──▶ [AI: 음식 이름만 식별] ──▶ [사용자 확인·보정] ──▶ [룰 엔진: 판정] ──▶ 결과
              틀려도 고칠 수 있음              안전장치           결정적·추적 가능
```

## 왜 이렇게 나눴나

이전 버전은 사진과 질환 목록을 통째로 Gemini에 던지고 판정까지 받아 왔다. 잘 작동하지만 세 가지 문제가 있었다.

**검증할 수 없다.** "된장찌개는 고혈압에 주의"라는 답이 왔을 때, 나트륨 몇 mg을 어떤 기준과 비교해서 나온 결론인지 알 수 없다. 보고서에 근거를 댈 수 없고, 틀렸을 때 어디를 고쳐야 할지도 모른다.

**재현되지 않는다.** 같은 밥상을 오늘 찍으면 "주의", 내일 찍으면 "좋음"이 나올 수 있다. 건강 판정에서 이건 치명적이다.

**오류를 잡을 수 없다.** 식별이 틀리면 사용자가 눈으로 보고 고칠 수 있다. 판정이 틀리면 아무도 모른다.

그래서 AI에게는 "사진에 무엇이 있는가"만 묻고, "그것이 이 사람에게 좋은가"는 코드로 계산한다. 판정 근거가 임계값·수치·출처까지 전부 화면에 나온다.

## 바로 실행하기

### 1. 더블클릭 — 가장 빠름

`dist/index.html`을 더블클릭하면 열린다. 서버도 설치도 필요 없다. 소스와 영양 테이블 148종이 한 파일(216KB)에 들어 있다.

사진 올리기와 판정은 정상 동작한다. **자동 인식은 브라우저에 따라 막힐 수 있다** — `file:` 출처에서 CDN 동적 import를 차단하는 경우가 있다. 막히면 그때 이유와 대안을 안내하고 검색창으로 넘긴다.

> **여기서 두 번 실수했다.** 처음에는 `file://`을 감지해 조용히 "직접 고르기"로 전환하고 사진 영역을 통째로 숨겼다. 사용자에게는 **사진 업로드가 이유 없이 사라진 것**이었다. 두 번째로는 안내 배너를 붙였는데, 이번엔 열자마자 경고문부터 읽히는 꼴이 됐다. 둘 다 근본 원인은 같다 — **실제로 막히는지 확인도 안 하고 미리 차단한 것.**
>
> 지금은 아무것도 미리 막지 않는다. 사진 올리기는 어느 환경에서든 되므로 항상 열어 두고, 자동 인식은 일단 시도한다. 실패하면 그때 원인에 맞는 안내를 하고 검색창으로 포커스를 옮긴다. 막다른 길이 생기지 않는 것이 핵심이다.

### 2. `열기.command` 더블클릭 — 자동 인식이 막힐 때

로컬 웹서버를 띄우고 브라우저를 여는 스크립트다. 빌드 파일이 없으면 알아서 만들고, 8000번 포트가 쓰이고 있으면 빈 포트를 찾는다. 1번에서 자동 인식이 막혔다면 이쪽으로 열면 된다.

macOS가 처음에 "확인되지 않은 개발자" 경고를 띄우면 파일을 **우클릭 → 열기**를 한 번 해 주면 된다.

### 개발용 — 모듈 구조

```bash
npm run build    # 원본을 고쳤을 때 다시 빌드
npm run serve    # http://localhost:8000
```

**설정 없이 그대로 동작한다.** API 키도 필요 없다(자체 모델·직접 고르기로 동작). `file://`로 직접 열면 ES 모듈이 CORS에 막히므로 이쪽은 반드시 서버를 띄운다. 그래서 단일 파일 빌드가 따로 있다.

> **file://에서 겪은 실제 버그**: `localStorage`는 opaque origin에서 접근만 해도 예외를 던진다. 초기화 첫 줄에서 이걸 감싸지 않았더니 스크립트 전체가 죽어 흰 화면이 나왔다. `test/dist.test.mjs`가 이걸 잡았고, 지금은 안전 래퍼를 거쳐 저장이 안 되면 메모리로 조용히 대체한다. 시크릿 모드·쿠키 차단에서도 같은 문제가 생긴다.

테스트 (총 513건):

```bash
npm install      # 테스트 전용 의존성(jsdom)
npm test         # 513건 전부 + 빌드

npm run test:rules        # 룰 엔진 143건
npm run test:integration  # 데이터 계층 174건
npm run test:ui           # 모듈 구조 UI 흐름 91건 (jsdom)
npm run test:dist         # 배포 산출물 105건 (file:// 환경 재현 + PWA + 면책 게이트)
npm run test:clip         # CLIP API 계약 9건
```

`dist.test.mjs`가 특히 중요하다. 빌드 산출물을 `file://` origin으로 jsdom에 올려 **스크립트를 실제로 실행**한다(`runScripts: 'dangerously'`). 브라우저가 그 파일을 여는 것과 거의 같은 경로라, 번들링 오류와 `file://` 고유 문제를 여기서 잡는다.

`ui.test.mjs`는 실제 `index.html`을 jsdom에 올리고 `app.js`를 그대로 실행한 뒤, 사람이 하는 순서대로 클릭·입력해 결과 화면까지 도달하는지 본다. 질환 선택, 프로필 저장·복원, 음식 검색·추가·양 변경·삭제, 판정, 근거 렌더, 어댑터 전환, 다시하기, XSS 방어를 커버한다.

**다만 jsdom이 검증하지 못하는 것이 있다.** 카메라·파일 선택(canvas 없음), CLIP 모델 다운로드·추론(WebGPU/WASM 없음), 그리고 레이아웃·스타일(jsdom은 CSS를 계산하지 않는다). 이 셋은 실제 브라우저에서 한 번 확인해야 한다.

판정과 화면 흐름은 검증됐다. 사진 인식은 **돌아가지만 한국 음식 정확도가 낮다** — 원인과 대응은 아래에 정리했다.

### CLIP은 무엇이 확인됐나

`test/clip-smoke.mjs`가 설치된 패키지 소스에서 API 계약을 직접 읽어 확인한다. 네트워크 없이도 돈다.

```bash
npm install @huggingface/transformers@3.7.5
node test/clip-smoke.mjs                    # 계약 검증
node test/clip-smoke.mjs ./밥상사진.jpg      # 인터넷 되면 추론까지
```

확인된 것: 태스크명 `zero-shot-image-classification`이 등록돼 있고, 호출 시그니처가 `(images, candidate_labels)`이며, 반환이 `{score, label}` 배열에 내림차순 정렬돼 있다. 라이브러리 자체 예제도 같은 모델(`Xenova/clip-vit-base-patch32`)을 쓴다. `identify.js`가 가정한 것과 전부 일치한다.

사진 입력 경로도 소스를 따라가 확인했다. 앱은 canvas로 만든 dataURL 문자열을 넘기고, `RawImage.read(string)` → `fromURL` → `fetch(dataURL)` → `.blob()`으로 이어진다. `fetch`에 dataURL을 넣으면 status 200과 올바른 MIME의 Blob이 나오므로 이 경로는 막히지 않는다.

확인 안 된 것: 모델 가중치가 실제로 받아지는지, WebGPU/WASM 추론이 도는지, 그리고 **한국 음식을 얼마나 맞히는지**.

### 한국 음식 인식률이 낮다 — 원인과 대응

실제로 써 보니 한국 음식을 잘 못 맞힌다. 원인은 두 가지다.

**하나, CLIP이 한국 음식을 거의 못 봤다.** 이 모델은 웹 이미지의 영어 alt-text로 학습됐다. 김치·비빔밥·불고기처럼 영어권에 널리 알려진 것은 알지만, 깍두기와 배추김치를 가르거나 된장찌개와 청국장을 구분하는 데 필요한 데이터는 학습에 거의 없었다. 이건 모델을 바꿔도 근본적으로 해결되지 않는다.

**둘, 라벨을 잘못 줬다 — 이건 고쳤다.** 초기 라벨은 요리 이름 위주였다.

```
(전) "doenjang jjigae, Korean soybean paste stew"
(후) "a bubbling brown soybean paste stew with tofu and zucchini in an earthenware pot"
```

CLIP은 이름이 아니라 **생김새**로 매칭한다. 프롬프트 템플릿이 `This is a photo of {}`이므로 뒤에 붙는 문장이 사진을 묘사할수록 잘 맞는다. 148종 전부를 색·그릇·건더기·질감 중심으로 다시 썼고, 특히 헷갈리는 묶음은 일부러 다른 특징을 앞세웠다.

| | 앞세운 특징 |
|---|---|
| 된장찌개 | **brown** stew, earthenware pot |
| 김치찌개 | deep **red**, pork slices, shallow pot |
| 순두부찌개 | bright red, **black stone bowl** |
| 시금치나물 | **dark green** wilted |
| 콩나물무침 | **pale yellow** crunchy |

테스트가 이 구분을 고정한다(`integration.test.mjs`).

**셋, 확신이 없으면 담지 않는다.** 신뢰도 0.35 미만이면 1등을 조용히 담지 않고 후보 5개를 눌러 고르게 한다. 잘못 담긴 채로 판정받는 것보다 한 번 더 누르는 편이 안전하다.

### 그래도 정확도가 필요하면

| 방법 | 효과 | 비용 |
|---|---|---|
| **Gemini 어댑터** | 크다. 한국 음식을 실제로 안다 | 본인 API 키 등록 필요(무료 등급), 사진 외부 전송 |
| 모델 교체 (SigLIP·CLIP-L) | 작다 | `ONDEVICE_MODELS`에서 한 줄. 다운로드 용량 증가 |
| 직접 고르기 | 100% | 검색 몇 초 |

`js/identify.js`의 `ONDEVICE_MODELS`에 세 모델을 등록해 뒀으니 바꿔 가며 비교할 수 있다. 다만 **어느 것도 한국 음식으로 학습되지 않았다.** 모델을 키운다고 된장찌개와 김치찌개를 확실히 가르게 되지는 않는다.

정확도가 정말 중요하면 답은 Gemini다. 사진이 외부로 나가는 것을 감수할지가 판단 기준이고, 그래서 어댑터를 교체 가능하게 만들었다.

**애초에 설계가 이 전제 위에 서 있다.** 판정은 AI가 하지 않고, 인식 결과는 반드시 확인 화면을 거치며, 신뢰도가 낮으면 아예 담지 않고 고르게 한다. 인식이 틀려도 사용자가 잡을 수 있으면 앱은 여전히 쓸모가 있다. 이건 인식률이 낮을 것을 예상하고 짠 구조지, 사후 변명이 아니다.

> **실제로 있었던 버그**: 초기 구현은 CLIP 상위 5개를 전부 목록에 담았다. 분류 모델의 상위 N개는 "사진 속 음식 N개"가 아니라 "같은 사진에 대한 N개의 경쟁 추측"인데 이걸 혼동한 것이다. 밥 한 공기를 찍으면 밥+죽+잡곡밥+떡+비빔밥이 담겨 영양이 다섯 배로 합산되고 판정이 통째로 틀어졌다. 지금은 1등만 담고 나머지는 "혹시 이건가요?" 후보로 분리한다. `integration.test.mjs`가 회귀를 막는다.

## 식별 어댑터 4종

설정 메뉴에서 언제든 바꿀 수 있다. **어느 것을 쓰든 판정 기준은 동일하다.** 인식 정확도와 사진의 행선지만 달라진다.

| | 정확도 | 사진 전송 | 설정 | 비용 |
|---|---|---|---|---|
| **자체 모델** (직접 학습, 기본값) | 한국 음식 최고 | **없음** | 불필요 (이미 학습돼 포함됨) | **0원** |
| **AI로 인식** (Gemini) | 높음 | **있음** — Google | 키 발급 2분 | 무료 등급 |
| **기기에서 인식** | 낮음 | 없음 | 불필요 | 완전 무료 |
| **직접 고르기** | 100% | 없음 | 불필요 | 완전 무료 |

**기본값은 자체 학습 모델이다.** Gemini 키를 아직 등록하지 않은 상태에서는 이 모델이 자동으로 쓰이고, 사진이 기기 밖으로 전혀 나가지 않는다. 키를 등록하면 그 순간부터 더 정확한 Gemini로 자동 전환된다.

> **한때 있었던 다섯 번째 어댑터: Pollinations(클라우드 AI).** 회원가입·키 없이 쓸 수 있다는 오래된 문서만 보고 기본값으로 넣었다가, 실제로는 익명 호출이 크레딧제로 바뀌어 열자마자 `402`가 났다 — **실제로 호출해 보지 않고 문서만 믿은 것**이 원인이었다(위 `file://` 사례와 같은 종류의 실수). 이후 토큰 발급 안내까지 붙여 살려 뒀지만, 어차피 토큰 발급이 필요해 Gemini와 설정 부담이 같은데 정확도·안정성은 더 낮았고, 세계 각지 사용자가 같은 익명 쿼터를 나눠 쓰는 구조라 그마저도 자주 429가 났다. 2026-08-22에 통째로 걷어냈다 — `PollinationsIdentifier`·`POLLINATIONS_TOKEN`·`CLOUD_READY`는 git 이력에만 남아 있다.

온디바이스는 `Xenova/clip-vit-base-patch32`를 Transformers.js로 브라우저에서 돌린다. 내장 테이블의 영문 설명문을 후보로 주는 제로샷 분류라 **테이블에 없는 음식은 원리적으로 못 맞힌다.** WebGPU가 있으면 GPU, 없으면 WASM으로 떨어진다(느림).

## 유료 앱으로 낼 때의 원가 구조

구독제로 출시하면 **무료 등급은 못 쓴다.** 한도가 사용자별이 아니라 API 키 단위라 전체 사용자가 하루 250회를 나눠 쓰게 되고, 무료 등급은 구글이 입력을 제품 개선에 쓴다. 남의 밥상 사진으로 그럴 수 없다. 유료 등급으로 가야 하고, 유료 등급은 데이터를 학습에 쓰지 않는다.

**그런데 원가 자체는 작다.** Flash-Lite 입력 100만 토큰에 $0.10이고, 1024px 사진 한 장은 프롬프트·출력까지 합쳐 대략 1,500토큰 안쪽이다. **1,000끼 판정에 1달러가 안 된다.**

### 호출을 줄이는 네 겹

원가를 낮추는 진짜 방법은 "AI를 싸게"가 아니라 **"AI를 덜 부르는 것"**이다. 실제 식단 기록 앱들이 LLM으로 매 끼를 인식하지 않는 이유다.

| 수단 | 효과 | 상태 |
|---|---|---|
| **최근 먹은 것** | 가장 큼. 사람은 같은 걸 반복해 먹는다 | ✅ 구현 |
| **검색 우선** | 큼. 148종 + 식약처 수만 종 | ✅ 구현 |
| 해상도 낮추기 | 토큰 비례 감소 | 🔧 도구만 (실측 필요) |

최근 목록은 담았던 음식을 칩으로 띄운다. 누르면 **AI 호출이 0회**다. 검색창보다 위에 두어 이 경로가 먼저 눈에 들어오게 했다.

### 서버측 쿼터는 걷어냈다 (2026-08-22)

원래는 Cloudflare Worker 프록시가 API 키를 대신 들고 있으면서 호출 전에 쿼터를 확인하고 성공한 뒤에만 차감하는 구독제 과금 구조를 실험했다(등급별 하루 한도, 기기 토큰으로 사용자 구분). 그런데 이 프록시가 죽거나 배포가 밀리면 **본인 키를 붙여넣었는데도 인식이 안 되는** 상황이 실사용에서 반복됐다 — 사용자 키가 있어도 항상 프록시를 거치도록 짜여 있었기 때문이다.

지금은 그 계층을 통째로 걷어냈다. Gemini는 예외 없이 **사용자 본인의 API 키로 구글에 직접** 붙는다(BYOK). 서버가 없으니 서버가 죽어서 안 되는 경우 자체가 없고, 원가도 우리 쪽에 전혀 없다. 대신 사용량 상한은 기기 안 로컬 카운터(참고용, 실제 집행은 구글 쪽 429가 한다)로만 안내한다. 구독제로 다시 만들려면 이 계층을 되살려야 하는데, 그건 계정·결제 검증과 함께 다시 설계해야 할 별도 작업이다.

## 개인이 쓸 때 — 돈이 안 든다

이 앱은 **전부 무료로 운영할 수 있다.** 어느 어댑터를 쓰든 마찬가지다.

| 어댑터 | 비용 | 한도를 넘기면 |
|---|---|---|
| 자체 모델 (기본값) | 무료. 내 기기에서 계산 | 한도 없음 |
| Gemini | **무료 등급. 신용카드 불필요** | 429 → "잠시 후" 안내 |
| 기기에서 인식 | 무료. 내 기기에서 계산 | 한도 없음 |
| 직접 고르기 | 무료. AI를 안 씀 | 한도 없음 |

**Gemini 무료 등급은 신용카드가 필요 없고 기간 제한도 없다.** 결제(billing)를 활성화하지 않는 한 청구가 발생할 수 없다. 한도를 넘기면 돈이 나가는 게 아니라 `429`가 오고, 앱은 안내를 띄운 뒤 검색으로 담도록 넘긴다. 어느 경로에서도 요금이 나갈 구멍이 없다.

**다만 AI Studio에서 결제를 켜는 순간 무료 등급이 사라진다.** 켜지 말 것. 나중에 유료 전환이 필요하면 테스트용과 운영용 프로젝트를 분리하는 편이 안전하다.

호스팅도 무료다. GitHub Pages 무료 등급으로 충분하다.

### Gemini를 바로 시험해 보려면

[aistudio.google.com](https://aistudio.google.com)에서 키를 받아 `js/app.js`의 `DEV_GEMINI_KEY`에 붙여넣고 `npm run build`만 하면 된다.

**이 키가 든 파일을 인터넷에 올리면 누구나 훔쳐 쓴다.** 품질만 확인하고 반드시 지울 것. 실사용자는 이 값을 안 쓰고 전부 설정 화면에서 본인 키를 직접 붙여넣는다(BYOK) — 배포 워크플로도 산출물에 `DEV_GEMINI_KEY`가 채워진 채로 섞이면 배포를 막는다.

세 방식의 인식 정확도를 같은 사진으로 비교해 표로 만들면 보고서 실험 섹션이 하나 나온다. 판정 로직이 고정돼 있으니 식별 정확도만 깨끗하게 분리 측정된다.

## 룰 엔진

`js/rules.js`의 임계값에는 전부 `RATIONALE` 주석이 달려 있다. 예:

```js
hi('potassium_mg', 400, 700,
  'RATIONALE: 진행된 만성콩팥병(3b기 이상)에서 1일 칼륨 2,000~2,500mg 제한이 흔하다. ' +
  '3끼+간식으로 나누면 1끼 약 600mg. 고칼륨혈증은 부정맥·심정지로 직결되므로 보수적으로 잡는다.', …)
```

이 문장이 그대로 화면의 "판정 근거 보기"에 나온다.

| | 임신·수유 중 | 알코올, 카페인, 레티놀, 요오드, 나트륨, 생식품, 수은 |

### 개인 프로필은 전부 선택 입력

체중·나이·성별을 넣으면 임계값이 조정되고, 넣지 않으면 성인 60kg 기준으로 판정한다. **입력을 강제하지 않는 것이 설계 결정이다.** 건강 앱에서 개인정보 입력을 요구하면 쓰지 않게 되고, 강제해서 얻는 정확도보다 안 쓰게 되는 손실이 크다. 입력값은 브라우저 `localStorage`에만 남고 어떤 서버로도 전송되지 않는다.

| 입력 | 영향 |
|---|---|
| 체중 | 콩팥병 단백질(0.35·0.5 g/kg), 심부전 수분(5·8.3 ml/kg) |
| 나이 | 섭취 기준 축 전체에 연령 계수 (6세 미만 0.5 ~ 성인 1.0, 75세 이상 0.9) |
| 성별 | 철·칼슘 안내 참고 |

같은 불고기 한 접시(단백질 27g)가 45kg이면 `피함`, 90kg이면 `좋음`으로 갈린다. 조정이 일어나면 근거 화면에 "체중 45kg 기준으로 조정됨"이라고 표시한다.

연령 계수는 정밀한 소아 영양 기준표를 넣기 전까지의 보수적 근사다. 한국인 영양소 섭취기준의 연령별 권장량이 체격에 거의 비례한다는 점에 기댄 것이고, 나이를 입력하지 않으면 적용되지 않는다.

### 특별히 신경 쓴 다섯 가지

**와파린은 "금지"가 아니라 "일관성"이다.** 비타민K가 많은 음식이 나쁜 게 아니라, 평소보다 갑자기 많이 먹는 것이 INR을 흔든다. 그래서 이 질환만 메시지가 "드시지 마세요"가 아니라 "평소와 같은 양을 유지하세요"이고, overall 판정을 끌어내리지 않는다. 여기서 "시금치 피하세요"라고 말하면 정반대의 조언이 된다.

**연하곤란은 영양소를 전혀 보지 않는다.** 떡은 나트륨·당·지방 어느 기준으로도 문제가 없지만 국내 질식사고 원인 1위다. 고령층에서 가장 흔하지만 뇌졸중·파킨슨병·두경부암으로 젊은 층에도 생기고, 소아 질식사고에서도 떡은 상위다. 그리고 반직관적으로 **묽은 액체가 걸쭉한 것보다 위험하다** — 흐름이 빨라 후두가 닫히기 전에 기도로 들어간다. 물·우유에 `주의`가 뜨는 게 버그가 아닌 이유다.

**미역국 한 그릇이 요오드 하루 상한을 넘긴다.** 건미역의 요오드 농도가 극단적으로 높아 한 그릇에 약 2,500µg, 한국인 상한 2,400µg을 넘는다. 하필 산후조리에 미역국을 매 끼 먹는 관습이 있어서, 임신·수유와 갑상선을 함께 고르면 이 충돌이 그대로 드러난다. 한국 식단에서 요오드는 결핍이 아니라 과잉이 문제라 룰도 과잉만 판정한다.

**임신 판정에서 레티놀과 베타카로틴을 구분했다.** 소간 100g의 레티놀은 약 9,000µg으로 임신 중 상한(3,000µg)의 세 배다. 그런데 같은 '비타민A'라도 식물성 베타카로틴은 체내 전환이 조절돼 과잉 독성이 없다. 둘을 합쳐 계산하면 시금치·당근이 부당하게 경고를 받는다. 그래서 `vita_ug` 축은 **동물성 레티놀만** 계상하고, 테스트로 식물성 식품의 값이 0인지 검증한다.

**빈혈은 "나쁜 음식"이 아니라 "나쁜 조합"이다.** 불고기 단독은 `좋음`이지만 커피를 곁들이면 `주의`가 된다. 커피·차의 폴리페놀이 비헴철 흡수를 최대 60~90% 억제하기 때문이다. 음식을 금지하는 게 아니라 시간을 띄우라고 안내한다. 골다공증과 함께 고르면 칼슘도 같은 문제를 일으켜 충돌 안내가 뜬다.

### 질환·상태 충돌

여러 개를 고르면 권고가 정면으로 부딪히는 경우가 생긴다. 코드에 명시적 충돌 규칙을 뒀다.

| 충돌 | 처리 |
|---|---|
| 칼륨 (고혈압 ↔ 만성콩팥병) | 콩팥병 우선. 고혈압 쪽 칼륨 가점을 억제하고 이유를 화면에 표시 |
| 단백질 (골다공증 ↔ 만성콩팥병) | 콩팥병 우선. 칼슘·비타민D로 보완하라고 안내 |
| 비타민K (와파린 ↔ 전체) | 승자 없음. 판정 성격이 다르다는 설명을 표시 |
| 수분 (심부전 ↔ 연하곤란) | 승자 없음. 국물은 줄이되 물은 점도증진제를 쓰라고 안내 |
| 철·칼슘 (빈혈 ↔ 골다공증) | 승자 없음. 끊지 말고 끼니를 나누라고 안내 |
| 요오드 (임신 ↔ 갑상선) | 갑상선 우선. 보충제 여부는 담당의와 상의하라고 안내 |
| 열량 (임신 ↔ 지방간·비만) | 승자 없음. 임신 중 임의 감량 금지를 명시 |

바나나 하나로 이걸 확인할 수 있다. 고혈압만 고르면 `좋음` + 칼륨 칭찬, 콩팥병을 추가하면 `주의` + 충돌 안내로 바뀐다.

### 룰이 다루지 못하는 범위는 스스로 밝힌다

갑상선 판정에는 `note`가 붙어 "이 판정은 요오드 과잉만 봅니다. 항진증·저하증 구분과 레보티록신 복용 시점은 반영하지 않습니다"라고 결과 화면에 표시된다. 룰 엔진이 커버하지 못하는 영역을 침묵으로 넘기면 사용자가 커버된다고 오해한다.

## 영양 데이터가 2계층인 이유

식약처 식품영양성분DB는 에너지·탄수화물·단백질·지방·당류·나트륨·콜레스테롤·포화지방·트랜스지방을 준다. 그런데 판정에 필요한 축 상당수가 빠진다.

- **퓨린** — 항목 자체가 없다. 통풍 판정에 필수
- **비타민K** — 커버 불완전. 와파린 판정에 필수
- **칼륨·인** — 품목에 따라 누락. 만성콩팥병 판정에 필수
- **요오드** — 없다. 갑상선·임신 판정에 필수
- **철·카페인·레티놀** — 없거나 불완전. 빈혈·임신 판정에 필수
- **질감·자극성·태그** — 영양 DB의 개념이 아니다. 연하곤란·역류·임신 판정에 필수

그래서 내장 테이블을 항상 기반으로 깔고, 식약처 값이 있으면 겹치는 축만 덮어쓴다. 오프라인에서도 판정이 되고, 온라인이면 정확도가 오른다. 결과 화면 하단에 **몇 %가 식약처 값이고 몇 %가 추정치인지** 표시한다.

### 식약처 API 검증 (해야 할 일)

`I2790`은 2023년으로 신규 제공이 끝났고 후속이 `I0750`이다. `js/nutrition.js`의 `MFDS_PROFILES.I0750`은 **필드명과 basis가 미검증 상태**로 들어가 있다. 실제 키를 발급받아 한 번 호출하고 응답을 보고 확정해야 한다.

```bash
curl "http://openapi.foodsafetykorea.go.kr/api/{키}/I0750/json/1/3/FOOD_NM_KR=된장찌개" | jq .
```

확인할 것: ① 필드명이 `AMT_NUM*`가 맞는지 ② 값이 100g 기준인지 1회 제공량 기준인지(`basis`) ③ 칼륨·인이 실제로 채워져 있는지.

## 배포

### GitHub Pages

`.github/workflows/deploy.yml`이 push마다 테스트를 돌리고, **하나라도 깨지면 배포하지 않는다.** 룰 엔진이 잘못된 채로 나가면 사용자가 잘못된 식이 판단을 하게 되므로 이 게이트는 뺄 수 없다.

1. 저장소 → Settings → Pages → Source를 **GitHub Actions**로 변경
2. `main`에 push하면 자동 빌드·배포
3. 배포 주소: `https://<계정>.github.io/<저장소>/`

`start_url`과 모든 경로가 상대경로라 하위 경로 배포에서도 동작한다. 배포 직전 산출물에 API 키가 섞였는지 한 번 더 검사한다.

### 로컬에서 빌드 확인

```bash
npm run icons    # 아이콘 디자인을 바꿨을 때만
npm run build
npx serve dist   # 또는 cd dist && python3 -m http.server 8000
```

서비스워커는 `https` 또는 `localhost`에서만 등록된다. `file://`로 열면 PWA 기능 없이 앱만 동작한다.

### 배포 전 확인할 것

- [ ] 실제 브라우저에서 사진 인식이 되는지 (여전히 미검증 구간)
- [ ] 모바일에서 레이아웃이 깨지지 않는지
- [ ] 홈 화면에 추가했을 때 아이콘·이름이 제대로 나오는지
- [ ] `privacy.html`의 저장소 주소를 본인 것으로 수정

## 배포에 앞서 — 책임 범위

이 앱은 건강 판정을 내리므로 배포에 따르는 책임이 일반 웹앱과 다르다. 세 겹으로 대응했다.

**첫 실행 면책 고지.** 앱을 열면 고지 화면이 뜨고 체크박스에 동의하기 전에는 쓸 수 없다. 의료기기가 아니라는 점, 영양 수치가 검증 전 추정치라는 점, 통풍·와파린·갑상선·빈혈·임신 판정이 특히 부정확하다는 점, 응급 상황에는 119에 연락하라는 점을 명시한다. 고지 내용이 바뀌면 저장 키의 버전이 올라 다시 확인받는다.

**결과 화면의 상시 출처 표시.** 판정 아래에 항상 어떤 수치가 어디서 왔는지, 어떤 축이 추정치인지 나온다. 숨기지 않는다.

**개인정보 처리방침.** 어댑터마다 사진의 행선지가 완전히 다르다는 점을 표로 명시했다. 기본값은 사진이 기기를 떠나지 않는 모드이고, "AI로 인식"을 직접 켜야만 외부로 전송된다.

그럼에도 **영양 데이터가 검증되지 않았다는 사실은 변하지 않는다.** 실사용자를 본격적으로 받기 전에 영양사 검토를 거치는 것이 맞다.

## 알려진 한계

보고서의 한계 섹션에 그대로 쓸 수 있는 항목들이다.

**영양 테이블 값이 검증되지 않았다.** 148종 중 대부분이 일반 조리법 기준 추정치(`src: "est"`)다. 조리법·브랜드·지역에 따라 나트륨은 두 배까지 차이 난다. 특히 외식·프랜차이즈 음식(피자·버거·마라탕)은 업체별 편차가 가정식보다 크다. 실사용 전에 영양사 검토가 필요하다. `data/foods-ko.json`의 `src` 필드로 항목마다 출처가 구분돼 있다.

**퓨린·비타민K·요오드·철·카페인·레티놀은 전량 문헌 추정치다.** 공공 DB에 없어서 대체 방법이 없다. 통풍·와파린·갑상선·빈혈·임신 판정은 다른 항목보다 정확도가 구조적으로 낮으며, 앱이 이 사실을 결과 화면에 명시한다.

**소아 기준이 근사다.** 나이를 입력하면 연령 계수를 곱하는 방식인데, 이건 체격 비례 근사이지 소아 영양 기준표가 아니다. 실제 소아 권장량은 영양소마다 성인 대비 비율이 다르다(칼슘은 성장기에 오히려 성인보다 높다). 소아를 주 대상으로 쓰려면 연령별 기준표를 따로 넣어야 한다.

**임신 판정은 시기를 구분하지 않는다.** 임신 초기·중기·후기와 수유기의 요구량이 다르고 특히 레티놀 위험은 초기에 집중되는데, 지금은 하나로 묶어 처리한다.

**갑상선은 항진증·저하증을 구분하지 않는다.** 요오드 과잉만 판정하며 이 한계를 결과 화면에 표시한다.

**테이블 밖 음식은 처리하지 못한다.** 148종이 전부다. AI가 "아귀수육"을 식별해도 테이블에 없으면 목록에 못 넣는다. 이때 조용히 버리지 않고 "빠뜨리면 판정이 관대해집니다"라고 경고한다 — 누락된 나트륨이 판정을 실제보다 안전하게 보이게 만드는 것이 가장 위험한 실패 모드다.

**양 추정이 가장 큰 오차원이다.** 사진에서 그램을 정확히 알 수 없다. 사용자가 4분의 1~2인분 사이로 조정할 수 있게 했지만 여전히 어림이다. 짬뽕 1인분과 4분의 1이 서로 다른 판정으로 갈리는 걸 테스트로 확인해 뒀다.

**임계값은 일반 지침에서 유도한 것이다.** 개인의 병기, 신기능(eGFR), 투석 여부, 복용 약에 따라 실제 목표치가 다르다. 특히 만성콩팥병 단백질 룰은 **투석 전 기준**이라 투석 중인 환자에게는 정반대다. 앱이 이 문구를 함께 표시한다.

**의료기기가 아니다.** 진단·처방이 아닌 참고 정보임을 결과 화면에 상시 고지한다.

## 음식 테이블 구성

148종. 대상을 전 연령으로 넓히면서 한식 위주였던 초기 62종에 양식·분식·중식·일식·편의점·카페 음료·주류·간식 86종을 더했다.

카페인 축을 넣어 두고 급원이 믹스커피 하나뿐이었던 것이 대표적인 구멍이었다. 20~30대의 실제 카페인 급원은 에너지드링크·아메리카노·버블티인데 룰은 있고 데이터가 없어 판정이 작동하지 않았다. 지금은 9종이 카페인을 가진다.

| 분류 | 종수 | 비고 |
|---|---|---|
| 카페인 급원 | 9 | 아메리카노 150mg > 라떼 130 > 믹스커피 100 > 에너지드링크 80 |
| 가공식품 | 35 | 인 흡수율·대사 부담 판정에 사용 |
| 생식품(raw) | 8 | 임신 중 리스테리아 경고 |
| 알코올 | 5 | 소주·맥주·막걸리·와인·위스키 |
| 내장류 | 4 | 레티놀·퓨린·콜레스테롤 동시 고농도 |
| 수은 주의 | 2 | 생선회·참치캔 |

극단값이 룰의 임계값과 맞물리는지 확인해 두었다. 나트륨은 마라탕 3,200mg, 요오드는 다시마 5,400µg으로 각각 하루 기준을 한 끼에 넘긴다.

## 다음에 할 만한 것

- 영양사 검토를 거쳐 `src: "est"` 항목을 실측값으로 교체
- 프랜차이즈 음식은 업체별 공개 영양정보로 분화 (같은 '피자'라도 편차가 크다)
- 소아 연령별 영양 기준표를 넣어 근사 계수를 대체
- 임신 시기(초·중·후기·수유) 구분
- 식품 알레르기 축 추가 — 전 연령에서 수요가 크고 판정이 단순하다(포함 여부)
- 반복 식별용 캐시 — 같은 사진 재분석 방지
- PWA 매니페스트 + Service Worker로 완전 오프라인 설치형 전환
- 식별 정확도 실측: 같은 사진 50장에 대해 어댑터 4종 비교
